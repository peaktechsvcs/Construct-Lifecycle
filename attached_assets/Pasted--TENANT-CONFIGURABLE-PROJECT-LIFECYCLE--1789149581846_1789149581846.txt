============================================================
TENANT-CONFIGURABLE PROJECT LIFECYCLE & WORKFLOWS
============================================================

Add customer/tenant-level configuration for:

- Project lifecycle states
- Project statuses
- Lifecycle naming
- Lifecycle ordering
- Allowed state transitions
- Workflow rules
- Required actions before transition
- Role-based transition permissions
- Automation triggers
- Workflow templates

This must be configurable independently for each Construct Lifecycle software customer / tenant.

Do NOT hard-code one lifecycle for every customer.

============================================================
CORE PRINCIPLE
============================================================

Construct Lifecycle must provide a strong default project lifecycle, while allowing each software customer to customize how their organization operates.

Default Construct Lifecycle lifecycle:

Lead
→ Proposal
→ Awarded
→ Contracted
→ Pre-Construction
→ In Progress
→ Billing
→ Closeout

This remains the default template.

However, each tenant may:

- Rename states
- Add states
- Remove unused states
- Reorder states
- Archive states
- Create secondary statuses
- Configure allowed transitions
- Define workflow rules
- Define automation actions
- Create multiple workflow templates where permitted

Do NOT require every customer to use the exact default terminology.

============================================================
STABLE IDS — DO NOT USE DISPLAY NAME AS KEY
============================================================

Lifecycle states must use stable internal identifiers.

Example:

state_id:
lc_state_12345

Display Name:
Pre-Construction

If customer renames it to:

Project Preparation

the internal state ID remains unchanged.

Do NOT use:

"Pre-Construction"

as the permanent data relationship key.

This is essential for:

- Historical projects
- Reporting
- Integrations
- Audit logs
- Workflow rules
- API references

============================================================
ARCHIVE / REMOVE STATE
============================================================

Do not permanently delete lifecycle states that are referenced by historical projects.

If a state has been used:

Use:

Archive State

Archived states:

- remain on historical projects
- remain available in audit/history
- are excluded from new transitions by default
- remain reportable historically
- may be restored

If a state has never been used and has no dependencies, deletion may be allowed with confirmation.

Where is the project in the lifecycle?

============================================================
WORKFLOW VALIDATION
============================================================

Before Publish validate:

- At least one starting state
- No broken transitions
- No transition referencing archived/missing state
- No missing required rule configuration
- No duplicate display order conflicts
- No unreachable states unless intentionally allowed
- No state with invalid default status
- No circular automation conditions that would create loops
- No destructive mapping breakage

Show actionable errors.

Future migration UI may support:

→ New State

============================================================
FINAL RULE
============================================================

Do not treat the default Construct Lifecycle lifecycle as permanently hard-coded.

The default lifecycle is a STARTING TEMPLATE.

Each Construct Lifecycle software customer must be able to configure the terminology and workflow that matches how that organization actually performs construction work.

The architecture must be:

TENANT-CONFIGURED WORKFLOW
        ↓
STABLE LIFECYCLE IDs
        ↓
PROJECT STATE + STATUS
        ↓
VALIDATED TRANSITIONS
        ↓
RULES / APPROVALS / AUTOMATIONS
        ↓
DOMAIN EVENTS
        ↓
DASHBOARDS / REPORTING / API / INTEGRATIONS

Customer-facing labels may change.

Underlying identifiers, security, data integrity, audit, and integration behavior must remain stable.

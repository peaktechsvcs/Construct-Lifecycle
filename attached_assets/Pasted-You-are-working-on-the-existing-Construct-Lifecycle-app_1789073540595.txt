8. AUTHENTICATION AND TENANT CONTEXT
==================================================

When a user signs in:

1. Authenticate the user.
2. Determine their authorized tenant(s).
3. Establish the active tenant context.
4. Load that tenant's configuration.
5. Load that tenant's branding theme.
6. Load tenant-scoped application data.

The active tenant must be available to the backend for every protected request.

Never trust a tenant ID supplied directly by the client without validating that the authenticated user has access to that tenant.

11. ACCESSIBILITY GUARDRAILS
==================================================

Do not allow tenant branding to destroy accessibility.

Before a theme can be published:

- Validate required foreground/background contrast.
- Validate buttons.
- Validate links.
- Validate status indicators.
- Validate focus indicators.
- Validate important UI states.

Target WCAG 2.2 AA.

If a selected color combination fails accessibility:

- Show the administrator the problem.
- Explain which combination failed.
- Provide a suggested corrected value where practical.
- Prevent publishing of configurations that create unacceptable accessibility failures.

Do not rely exclusively on color to communicate status.

==================================================

Treat multi-tenancy as a security boundary.

Test:

- Tenant A cannot read Tenant B projects.

- Tenant A cannot retrieve Tenant B documents.
- Tenant A cannot access Tenant B branding.
- Tenant A cannot manipulate Tenant B IDs through API requests.
- Tenant A cannot access Tenant B records through search.
- Tenant A cannot access Tenant B records through exports.
- Tenant A cannot access Tenant B records through direct URLs.

Check authorization at the backend/data layer.

Do not rely on hidden frontend navigation as a security control.

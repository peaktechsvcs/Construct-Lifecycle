============================================================
CONSTRUCT LIFECYCLE — INTEGRATIONS, PUBLIC API,
SHARED DOMAIN SERVICES, AND SYSTEM-OF-RECORD ARCHITECTURE
============================================================

Implement an extensible integration platform for Construct Lifecycle.

This replaces prior separate integration prompts and should be treated as the governing architecture for:

- Native integrations
- Public API
- Webhooks
- Background synchronization
- Integration health
- System-of-record configuration
- Third-party connector development

IMPORTANT:

Do NOT rebuild the existing application.

Inspect the current codebase first.

Preserve the current Construct Lifecycle UI/UX, visual language, navigation behavior, multi-tenant model, environment model, customer branding entitlement model, lifecycle model, drilldown behavior, and security architecture.

The purpose of this work is to add a scalable integration architecture without changing the established product experience.

============================================================
CORE PLATFORM PRINCIPLE
============================================================

Construct Lifecycle is the PROJECT LIFECYCLE PLATFORM.

It should connect specialized systems rather than attempt to replace every specialized system.

Construct Lifecycle should remain authoritative for:

- Project lifecycle
- Operational project status
- Cross-system project relationships
- Follow-ups
- Workflow state
- Integration mappings
- Lifecycle activity
- Cross-system orchestration

External systems may remain authoritative for specialized domains such as:

- Accounting
- ERP
- Inventory
- Product information
- Takeoff
- Estimating
- Ecommerce
- Documents
- CRM

============================================================
API ENVIRONMENT ISOLATION
============================================================

API credentials belong to exactly one environment.

A Production credential cannot access D/T/D.

A D/T/D credential cannot access Production.

Authenticated identity determines tenant/environment.

Never trust caller-supplied customer_id as authorization.

============================================================
FINAL ACCEPTANCE CRITERIA
============================================================

[ ] Native integrations and Public API share the same domain/application services.

[ ] Integration providers do not directly implement independent business logic.

[ ] Construct Lifecycle uses a canonical data model.

[ ] Business Central is supported as an ERP/accounting provider.

[ ] QuickBooks is supported as an accounting provider.

[ ] MeasureSquare is supported as a specialized flooring integration.

[ ] STACK is supported as a specialized takeoff/estimating integration.

[ ] Shopify architecture is supported.

[ ] PIM integrations are supported.

[ ] New connectors can be added without redesigning the core application.

[ ] Integrations are tenant/customer scoped.

[ ] Integrations are environment scoped.

[ ] Production and D/T/D integrations remain isolated.

[ ] CLC Admin controls integration entitlements.

[ ] Disabled integrations are hidden from customer UI.

[ ] Customer user roles further restrict integration management.

[ ] Accounting/ERP System of Record can be configured.

[ ] Domain-level System of Record architecture is supported.

[ ] Multiple connected ERP/accounting providers may coexist without ambiguous ownership.

[ ] Construct Lifecycle remains authoritative for project lifecycle.

[ ] External mappings use stable IDs, not display names.

[ ] Public API is versioned.

[ ] Public API credentials are scoped and revocable.

[ ] Public API uses the same business rules as the UI.

[ ] Public API enforces tenant and environment isolation.

[ ] API rate limiting is supported.

[ ] Idempotent transactional operations are supported where needed.

[ ] Webhook architecture is supported.

[ ] Webhooks are signed and environment scoped.

[ ] Background integration processing is supported.

[ ] Integration failures support retries.

[ ] Repeated failures can enter manual-review state.

[ ] Integration health is visible.

[ ] Integration error counts are drillable.

[ ] Sync exceptions are actionable.

[ ] System-of-record changes are audited.

[ ] Integration configuration changes are audited.

[ ] Third-party outages do not prevent normal Construct Lifecycle project work.

[ ] Existing Construct Lifecycle UI/UX remains intact.

============================================================
FINAL IMPLEMENTATION RULE
============================================================

Do NOT build Construct Lifecycle as a collection of point-to-point integrations.

Build:

CONSTRUCT LIFECYCLE CANONICAL PLATFORM
+
SHARED APPLICATION / DOMAIN SERVICES
+
CONNECTOR ADAPTER FRAMEWORK
+
PUBLIC VERSIONED API
+
DOMAIN EVENTS
+
WEBHOOK FRAMEWORK
+
ASYNC SYNCHRONIZATION
+
SYSTEM-OF-RECORD CONTROL

External systems plug into Construct Lifecycle.

Construct Lifecycle's core application architecture must not need to be redesigned every time another ERP, accounting system, takeoff tool, PIM, ecommerce platform, CRM, or custom application is added.
